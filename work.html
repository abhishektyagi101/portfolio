Production RAG over engineering documentation

Siemens Energy · 2023 – present · Architect and technical lead

The problem

A service engineer standing next to a compressor needs a torque specification, a clearance tolerance or a commissioning step. That number exists — in one of tens of thousands of PDFs, some typeset, some scanned from the 1980s, spread across document management systems with inconsistent metadata. Finding it took 20 to 30 minutes of manual searching, and the engineer often gave up and called someone instead.

What I built

A retrieval-augmented service over technical documentation and industrial sensor data. Documents are parsed with structure preserved, chunked in a way that keeps tables and section hierarchy intact, embedded and indexed for hybrid retrieval. A Model Context Protocol layer lets the model call tools that query live sensor history, so an answer can combine "what the manual says" with "what this machine is doing". 

ingest → structure-aware parse → chunk (tables + headings preserved)
       → embed → hybrid index (BM25 + vector)
                    ↓
query → retrieve → re-rank → ground → generate → citation check → answer
                                          ↑
                              MCP tools: sensor history, asset metadata

Engineering decisions that mattered

  • Refusal over fluency. A guardrail layer suppresses any answer that cannot be traced to a source document. The system says "I could not find this" rather than approximating. Engineers trust it more because of that, not less.
  • Citations are mandatory, not decorative. Every response returns the document and section it came from, so the answer is verifiable in ten seconds.
  • Hybrid retrieval. Pure vector search fails on part numbers and equipment codes. Lexical matching fails on paraphrased questions. Both, fused, works.
  • Cost routing. Simple lookups go to a smaller model; only genuinely hard synthesis reaches the frontier model. Response caching handles the long tail of repeated questions.

Outcome

Used daily by engineering and service teams at three international sites. Lookups that took 20–30 minutes return in under a minute. Average cost per request fell roughly 35% after the caching, batching and routing work.

Real-time anomaly detection for gas turbines

Siemens Energy · 2022 – present · Architect and technical lead

The problem

Condition monitoring was a human process: analysts reviewed trend plots on a schedule and flagged what looked wrong. That scales badly, misses slow drift between reviews, and depends entirely on who happens to be looking.

What I built

An event-driven pipeline on AWS. Sensor batches land, a Step Functions workflow orchestrates validation, feature construction and scoring against SageMaker endpoints, and anomalies fan out through SNS and SQS to the people who can act on them. Everything is asynchronous, so a slow model never blocks ingestion. 

sensor batch → S3 → EventBridge rule → Step Functions
                                          ├─ validate & align timestamps
                                          ├─ build features (rolling stats, residuals)
                                          ├─ SageMaker endpoint → score
                                          └─ threshold + hysteresis → SNS/SQS → alert

Engineering decisions that mattered

  • Residual modelling, not raw thresholds. Models (SVR, XGBoost, stacked ensembles) predict what a healthy machine should be doing given operating conditions; the residual between predicted and actual is what gets scored. That separates "this machine is degrading" from "this machine is working harder today".
  • Hysteresis and dwell time. The first version alerted on every threshold crossing and produced noise. Requiring an anomaly to persist before it escalates was the difference between a system people used and one they muted.
  • Alerts route to owners, not to a mailing list. Ownership metadata sits in the routing layer.

Outcome

Replaced manual condition-monitoring rounds and surfaces developing faults days earlier than the review cadence allowed.

  • EventBridge
  • Lambda
  • SageMaker
  • XGBoost
  • SVR
  • Time-series

An LLMOps practice, built from nothing

Siemens Energy · 2023 – present · Owner

The problem

The first generative AI prototype shipped without any of the machinery that makes a system maintainable. Prompts lived in source files and changed without review. Nobody could answer "is this release better or worse than the last one?" except by opinion. Cost was a monthly surprise.

What I built

ConcernWhat exists now
VersioningPrompts and models are versioned artefacts. A response can be traced back to the exact prompt and model that produced it.
TrackingMLflow for experiments, parameters and a registry of promoted model versions.
Release gateA golden evaluation set runs on every release. Groundedness and citation-accuracy regressions block the pipeline.
Human reviewSampled production answers get reviewed by domain engineers; disagreements feed back into the golden set.
MonitoringDrift, latency and cost per request on a dashboard, with CloudWatch alerting into on-call when p95 latency regresses.
GovernanceRole-based access control, secrets in AWS, EU data residency, and audit trails covering who asked what and which documents the answer read.

Outcome

Ungrounded answers fell roughly 40% across three release cycles — not from a better model, but from measuring the right thing and refusing to ship regressions.
