Architecture

Event-driven anomaly detection on AWS for rotating equipment

10 September 2026 · 13 min read

Condition monitoring for turbines and compressors is usually a human process on a schedule: an analyst opens trend plots, looks for something wrong, and moves on. That misses slow drift between reviews and scales linearly with headcount. This is the architecture we replaced it with, including the mistake that nearly killed it.

The shape of the problem

Rotating equipment produces continuous multivariate telemetry — vibration, temperatures, pressures, flow, speed, load. The signals are correlated, non-stationary, and heavily dependent on operating condition. A bearing temperature of 95°C is normal at full load on a summer afternoon and alarming at part load in February.

That single fact is why static thresholds fail. Set them tight and you drown in false alarms whenever the machine works hard. Set them loose and you only catch faults that were already obvious.

The architecture

  sensor batch ──► S3 (raw)
                     │
                     ▼
              EventBridge rule
                     │
                     ▼
          ┌──── Step Functions ────────────────────┐
          │                                        │
          │  1. validate    (schema, gaps, ranges) │
          │  2. align       (resample, timezone)   │
          │  3. features    (rolling stats,        │
          │                  lags, load context)   │
          │  4. score       (SageMaker endpoint)   │
          │  5. residual    (predicted vs actual)  │
          │  6. persist     (S3 curated + metrics) │
          │  7. decide      (threshold + dwell)    │
          └────────────────┬───────────────────────┘
                           │ anomaly
                           ▼
                       SNS topic
                     ┌─────┴─────┐
                     ▼           ▼
                SQS queue    notification
                     │        (owner only)
                     ▼
              downstream systems

Everything is asynchronous and every step is idempotent. A slow model never blocks ingestion, a failed step retries without duplicating alerts, and replaying a day of history is the same code path as real-time.

Why Step Functions rather than one big Lambda

Three reasons, all operational rather than aesthetic.

  • Visible failure. When something breaks at 03:00, the console shows which step failed and with what input. Reconstructing that from logs inside a monolithic function is materially slower.
  • Per-step retry policy. Feature computation can retry immediately. A SageMaker endpoint returning 429 needs exponential backoff. A validation failure should not retry at all — it should route to a dead-letter path and page someone about the data source.
  • Step-level timeouts. The 15-minute Lambda ceiling is a real constraint on backfills, and splitting the work lets each step have a budget appropriate to what it does.

Residual modelling, not raw thresholds

This is the core modelling decision. Rather than asking "is this value abnormal", we ask "is this value abnormal given what the machine is being asked to do".

A model learns the expected value of each target signal from operating context — load, speed, ambient conditions, upstream measurements. The anomaly score is computed on the residual between prediction and reality, normalised by the model's typical error. 

# Conceptually:
predicted = model.predict(operating_context)   # what a healthy unit would do
residual  = actual - predicted
score     = abs(residual) / rolling_std(residual, window="30d")

# score is roughly "how many typical errors away is this"

The effect is that hot summer afternoons stop generating alarms, because the model already expects the temperature to be high. What survives is genuine deviation: the machine behaving differently from how it behaved under the same conditions last month.

Model choices

ApproachWhere it earned its place
Support Vector RegressionSmooth, well-behaved signals with strong physical relationships. Stable, few parameters, and its errors are interpretable.
Gradient boosting (XGBoost)Signals with regime changes and interaction effects. Feature importances survive contact with domain experts, which matters for trust.
Stacked ensembleWhere individual models disagree in useful ways. Disagreement between base models is itself a signal worth surfacing.

Notably absent: deep sequence models. We tried them. On this data, with this volume, the accuracy gain did not justify the operational cost or the loss of interpretability. When a reliability engineer asks why the system flagged a machine, "bearing 3 temperature is running 4σ above what load and ambient predict" is an answer they can act on. An attention map is not.

Features that mattered

  • Rolling statistics over multiple horizons — 1 h, 24 h, 7 d. Fault signatures live at different time scales.
  • Rate of change, not just level. Slow drift is the entire point.
  • Explicit operating-regime flags: startup, shutdown, steady state, load transition. Model behaviour during transients is a different problem and mostly should be excluded.
  • Cross-signal ratios that encode physics — pressure ratios, temperature differentials, efficiency proxies.
  • Time since last maintenance event. Machines behave differently after an overhaul, and pretending otherwise generates a fortnight of false alarms every service.

The mistake: alert fatigue

The first version alerted on every threshold crossing. It was technically correct and operationally useless. Within two weeks the notifications were being filtered into a folder nobody opened, which is exactly the same outcome as having built nothing.

Three changes fixed it.

Dwell time

An anomaly must persist for a minimum duration before it escalates. A single sample above threshold is noise; a condition sustained for an hour is a condition.

Hysteresis

Separate thresholds for entering and leaving the anomalous state. Without this, a signal oscillating around the boundary generates an alert storm. 

ENTER = 3.5   # sigma
EXIT  = 2.5   # sigma
DWELL = timedelta(hours=1)

if not state.active and score > ENTER:
    if state.above_since and now - state.above_since >= DWELL:
        state.active = True
        emit_alert()
elif state.active and score < EXIT:
    state.active = False
    emit_clear()

Routing by ownership

Alerts go to the person responsible for that asset, not to a distribution list. Ownership metadata sits in the routing layer and is maintained as part of asset onboarding. An alert that arrives in a shared inbox belongs to nobody.

The lesson generalises. The hard part of anomaly detection is not detecting anomalies. It is producing a volume of alerts that a human being will keep reading in month six. Precision at a tolerable alert rate is the only metric that predicts whether the system survives.

Operating it

  • Monitor the pipeline as hard as the equipment. Silent ingestion failure is the worst outcome — no alerts looks identical to everything being fine. We alert on the absence of expected batches.
  • Drift detection on inputs. A sensor that has been recalibrated shifts the feature distribution, and the model will faithfully report an anomaly that is an instrumentation change.
  • Every alert gets an outcome label. Confirmed fault, known operating condition, sensor problem, unexplained. Without that feedback loop you have no path to improving precision, and precision is the whole game.
  • Retrain on a schedule and on drift, with the same evaluation gate on both paths.

What I would do differently

  1. Build the feedback loop first. We added outcome labelling months in, and lost months of training signal that we could not recover.
  2. Onboard fewer assets, better. Breadth early created a maintenance burden that slowed the modelling work. Depth on a handful of machines would have taught us more, faster.
  3. Involve reliability engineers in threshold setting from day one. They know which deviations matter. We derived thresholds statistically and then spent weeks re-deriving them socially.
