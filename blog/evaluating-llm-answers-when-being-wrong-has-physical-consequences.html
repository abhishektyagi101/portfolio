Evaluation

Evaluating LLM answers when being wrong has physical consequences

10 September 2026 · 12 min read

If your assistant recommends the wrong film, someone has a mediocre evening. If it recommends the wrong torque value, someone loosens a bolt that was holding something in place. These two systems should not be evaluated with the same metrics, and yet almost everybody uses the same metrics.

The standard evaluation toolkit — helpfulness ratings, pairwise preference, an LLM judge scoring "overall quality" out of ten — was designed for open-ended assistants where the goal is a good experience. In a maintenance or commissioning context the goal is different: the answer is either correct and traceable, or it should not have been given.

This is what we replaced it with.

Start with the golden set, before you build anything

The first artefact in the project should be a set of real questions with verified answers and verified source references. Not synthetic questions generated from your own documents — that measures whether your retriever can find text it already produced. Real questions, collected from the people who will use the system.

We collected ours from support tickets, from the questions engineers asked each other in chat, and from sitting with service teams and writing down what they looked up. Every entry looks like this: 

{
  "id": "gs-0142",
  "question": "What is the radial clearance for an A-300 rotor at standard conditions?",
  "expected_answer": "0.22 mm nominal, range 0.19–0.25 mm",
  "expected_sources": ["manual-4471#4.3.2", "manual-4471#table-4-7"],
  "answer_type": "numeric_with_tolerance",
  "criticality": "high",
  "must_not_contain": ["0.15"],
  "asked_by": "field service",
  "frequency": "weekly"
}

Three fields there are doing unusual work. criticality lets you weight failures by consequence rather than counting them equally. must_not_contain encodes the specific wrong answer you expect the system to produce — usually the value from a neighbouring row or a superseded revision. And frequency lets you weight by how often the question actually gets asked, so you optimise for reality rather than for corpus coverage.

A few hundred entries is enough to gate a release. Ours grew over time from production disagreements, which is the healthiest way for it to grow.

The metrics we actually gate on

Retrieval recall@k

Is the correct source in the candidate set at all? Measured against expected_sources. This is the ceiling metric — if recall@20 is 0.7, then 30% of questions are unanswerable no matter what happens downstream. Fix this before touching anything else.

Groundedness

Decompose the answer into atomic claims, and check each one against the retrieved context. Any claim not supported by retrieved text is ungrounded. This is where an LLM judge is legitimately useful — not scoring quality, but performing a narrow entailment check with the evidence in front of it. 

ENTAILMENT_PROMPT = """You are checking a single factual claim against source text.

CLAIM: {claim}
SOURCE: {chunk}

Answer with exactly one word:
SUPPORTED   - the source states this claim
CONTRADICTED - the source states something incompatible
NOT_FOUND   - the source does not address this claim
"""

Keep the judge's job small and mechanical. A judge asked "is this a good answer?" produces noise; a judge asked "does this sentence follow from this paragraph?" is reliable enough to gate on.

Numeric fidelity

A deterministic check, no model involved. Extract every numeric quantity with its unit from the answer. Every one of them must appear in a retrieved chunk with a matching unit. This catches unit conversions the model performed silently, digits transposed during generation, and values borrowed from an adjacent table row.

It is the cheapest check in the suite and it catches the most dangerous class of error. If you implement one thing from this post, implement this.

Citation accuracy

Does the cited section actually contain the claim? A citation that points at the wrong section is worse than no citation, because it manufactures confidence and passes casual inspection.

Appropriate refusal

Deliberately include questions whose answers are not in the corpus. Roughly 10% of our golden set is unanswerable by construction. The correct behaviour is refusal, and a release that starts answering those questions has regressed, even if every other metric improved.

Refusal rate belongs on the dashboard, next to accuracy. If it drops, the system has become more willing to guess. That is a regression, and no other metric will show it as one.

What we deliberately do not measure

MetricWhy it is excluded
Helpfulness / preference scoreRewards fluent confidence. The dangerous failure mode in this domain is a wrong answer that reads beautifully.
Answer length or completenessThe correct answer to "what is the torque spec" is a number and a source, not four paragraphs.
Semantic similarity to a reference"0.15 mm" and "0.25 mm" are nearly identical in embedding space and describe different machines.
User thumbs-up rate aloneUsers cannot detect errors in domains where they are consulting the system precisely because they do not know the answer.

That last one deserves emphasis. Thumbs-up data measures whether the answer felt satisfying, and in a lookup system the user has no independent way to know if it was right. We collect it, we look at it as a usability signal, and we never gate on it.

The release gate

Every change — prompt edit, model version, retrieval parameter, chunking change — runs the full golden set in CI. The pipeline blocks on regression, not on absolute thresholds: 

gate:
  recall_at_20:        {min: 0.92, max_regression: 0.01}
  groundedness:        {min: 0.95, max_regression: 0.01}
  numeric_fidelity:    {min: 0.99, max_regression: 0.00}   # zero tolerance
  citation_accuracy:   {min: 0.93, max_regression: 0.02}
  appropriate_refusal: {min: 0.90, max_regression: 0.02}
  high_criticality_failures: {max: 0}

Absolute thresholds tell you whether the system is good enough to exist. Regression limits stop the slow decay that happens when twenty small changes each cost half a percent and nobody is watching the cumulative total. The zero-regression rule on numeric fidelity is the one nobody is allowed to override.

Human review, sampled and structured

Automated evaluation cannot tell you whether the answer was useful in context, so we sample production answers weekly and have domain engineers review them. Two rules make this sustainable:

  1. Sample deliberately, not randomly. Weight toward high-criticality question types, low-confidence retrievals and answers where the model nearly refused. Random sampling of a system that is 95% correct wastes most of your reviewer's time confirming things that are fine.
  2. Every disagreement becomes a golden-set entry. This is the whole point. Human review that does not feed back into automated evaluation is a report, not a process. Ours grew by roughly 30% in the first year entirely from review findings.

What this bought us

Ungrounded answers fell by roughly 40% across three release cycles. The base model did not change. What changed was that we could see regressions before users could, and that shipping something worse became procedurally difficult rather than merely discouraged.

There is a second benefit that is harder to quantify and possibly more valuable. When a safety engineer asks "how do you know this thing is right?", the answer is a document with numbers in it and a CI pipeline that enforces them. That conversation is the difference between a pilot and a production system, and no amount of demo quality substitutes for it.

In safety-adjacent domains, evaluation is not quality assurance. It is the argument for why the system is allowed to exist.
