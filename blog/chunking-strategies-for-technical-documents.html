Retrieval

Chunking strategies for P&IDs, datasheets and scanned manuals

10 September 2026 · 11 min read

Every RAG tutorial starts with a recursive character splitter at 1000 tokens with 200 overlap. On technical documentation, that single default destroys more information than any other decision in the pipeline.

The reason is simple. A character splitter optimises for chunk size. Technical documents encode meaning in structure — hierarchy, tables, figure references, units. Size and structure are unrelated, so optimising one shreds the other. A tolerance table split across two chunks is not two half-useful chunks. It is two useless chunks, one of which will retrieve well and mislead.

Here are four strategies that work instead, roughly in order of how much they will improve your system.

1. Heading-path chunking

Chunk on document structure, and make every chunk carry its full heading path as a prefix. The path is cheap in tokens and enormously informative — both for the embedding and for the human reading the citation. 

# Bad — a naked fragment
"...maximum permissible value is 0.22 mm for standard operating
conditions. Refer to Table 4-7 for other frame sizes."

# Good — same fragment, self-describing
"Manual 4471 Rev C > Section 4: Rotor Assembly > 4.3 Clearances
 > 4.3.2 Radial Clearance

...maximum permissible value is 0.22 mm for standard operating
conditions. Refer to Table 4-7 for other frame sizes."

The retrieval improvement comes from context that the fragment alone does not carry. "Maximum permissible value" matches a hundred passages; "radial clearance, rotor assembly, maximum permissible value" matches one.

Implementation note: build the heading path during parsing, from the document outline or from font-size and numbering heuristics on unstructured PDFs. Do not try to recover it later — the information is gone once you have a flat string.

2. Table-atomic chunking

Never split a table. Treat it as an indivisible unit regardless of size, and if it genuinely exceeds your context budget, split by rows while repeating the header on every fragment.

Then serialise it in a form that survives embedding. Markdown pipe tables work reasonably well. Row-oriented natural language works better for retrieval, at the cost of tokens: 

# Markdown form — compact, good for the model to read
| Frame size | Nominal (mm) | Min (mm) | Max (mm) |
|------------|--------------|----------|----------|
| A-200      | 0.15         | 0.13     | 0.17     |
| A-300      | 0.22         | 0.19     | 0.25     |

# Row-expanded form — verbose, much better for retrieval
"Table 4-7 Radial clearance by frame size. For frame size A-200:
 nominal 0.15 mm, minimum 0.13 mm, maximum 0.17 mm."
"Table 4-7 Radial clearance by frame size. For frame size A-300:
 nominal 0.22 mm, minimum 0.19 mm, maximum 0.25 mm."

We index the row-expanded form and pass the markdown form to the model. Retrieval hits the specific row; generation sees the whole table and can reason across it. The duplication costs storage, which is the cheapest resource in the system.

3. Figure-caption binding

A P&ID or a cross-section diagram carries information that no text pipeline will extract. What you can do is make sure the surrounding text knows the figure exists and can point an engineer at it.

Bind every figure to a chunk containing its caption, its number, the page, and the paragraphs that reference it anywhere in the document. Cross-references are usually recoverable with a regex over "Figure 4-2", "Fig. 4-2", "see 4-2". 

{
  "type": "figure",
  "id": "fig-4-2",
  "caption": "Figure 4-2: Rotor assembly cross-section, A-series",
  "page": 84,
  "referenced_by": [
    "4.3.1: The bearing housing (Figure 4-2, item 7) must be...",
    "4.5.2: During reassembly, verify orientation per Figure 4-2."
  ],
  "asset_ref": "s3://.../manual-4471/p084-fig02.png"
}

The answer then becomes: "The bearing housing is item 7 — see Figure 4-2 on page 84 of Manual 4471 Rev C", with a link to the image. That is genuinely useful, and it is honest about the limits of the system. If you have vision-model budget, caption generation on the figure itself adds another retrieval surface, but the binding is what does most of the work.

4. Overlap by section, not by character

Character overlap exists to stop a sentence being cut in half. On structured documents you do not need it, because you are not cutting mid-sentence any more. What you need instead is semantic overlap: a chunk should carry a short summary of its parent section. 

chunk_text = (
    f"{heading_path}\n"
    f"[Section context: {parent_section_summary}]\n\n"
    f"{body}"
)

Generate the parent summary once per section at ingestion — one cheap model call per section, not per chunk. It resolves the pronoun problem ("it must be replaced" — what must?) far more reliably than 200 characters of arbitrary overlap.

Handling scanned documents

Scanned manuals deserve their own treatment because everything above assumes you have structure to work with, and OCR output frequently has none.

  • Keep a confidence score per block and store it on the chunk. Low-confidence regions should be retrievable but flagged, and any numeric value extracted from a low-confidence region should be excluded from the numeric-fidelity check rather than silently trusted.
  • Never auto-correct numbers. A spellchecker that fixes "recieve" is fine. One that "fixes" a part number is a defect generator.
  • Use layout-aware OCR that emits bounding boxes, then reconstruct reading order and table grids geometrically. Column-major reading order on a two-column scan is a common and completely silent corruption.
  • Prefer a re-scan over heroic parsing. If a document matters and the scan is bad, the cheapest fix is often to get a better source file, not to write more code.

A test that catches most chunking bugs. Take twenty chunks at random and read them cold, with no other context. If you cannot tell what equipment, which section and which revision each one is about, neither can the retriever, and neither can the model.

What this costs

Honestly: a lot more engineering than a character splitter, and a bigger index. Structure-aware parsing of a heterogeneous corpus is weeks of work, and the row-expanded table representation roughly doubles storage for tabular documents.

It is still the highest-return work available. Retrieval sets a ceiling on the entire system — if the right chunk is not in the candidate set, no model, no prompt and no amount of re-ranking will produce a correct answer. Everything downstream is optimisation under that ceiling.
